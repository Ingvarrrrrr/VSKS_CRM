# legal/ — правовые документы GALA

Каталог держит все юридически значимые тексты (публичные политики и внутренние
документы по 152-ФЗ) как markdown-исходники с подстановками, а не как готовый
текст, продублированный по фронтенду/бэкенду/приказам. Единственное место, где
живут реквизиты оператора, домен, почта, сроки по 152-ФЗ и версии документов —
`legal/operator.json` (см. ПРАВИЛО №6 в CLAUDE.md и `legal/CONTRACT.md`).

## Структура

```
legal/
  operator.json         единственный источник реквизитов и версий
  CONTRACT.md            контракт между исполнителями (границы, язык шаблонов)
  build.py                сборщик: CLI, оркестрация
  render_md.py             подстановки + мини-markdown → AST → HTML
  render_docx.py           AST → .docx (python-docx), детерминированная упаковка
  sources/public/*.md      тексты публичных документов (политика, согласие, cookie, оферта)
  sources/internal/*.md    тексты внутренних приказов и положений
  out/                     СГЕНЕРИРОВАНО, в git не хранится (см. .gitignore)
frontend/src/legal/
  documents.generated.ts  СГЕНЕРИРОВАНО build.py, править руками запрещено
backend/app/services/
  legal_generated.py      СГЕНЕРИРОВАНО build.py, править руками запрещено
```

Сборка производит ДВА артефакта из одного `operator.json`, оба коммитятся в
репозиторий (не в `.gitignore`, в отличие от `legal/out/*.docx`):

- `frontend/src/legal/documents.generated.ts` — для фронтенда (тексты и версии
  публичных документов, реквизиты оператора для страниц сайта);
- `backend/app/services/legal_generated.py` — для бэкенда (сроки ответа по
  152-ФЗ из `deadlines_working_days`, перечень документов согласия для
  регистрации). Существует, потому что образ бэкенда собирается из каталога
  `backend/` (`backend/Dockerfile`, `COPY . .`) и не видит `legal/` — до этого
  `backend/app/services/legal_constants.py` читал `legal/operator.json` по
  относительному пути от `__file__`, что работало локально, но приводило к
  `RuntimeError` при импорте в контейнере (файла там просто нет) и падению
  всего бэкенда/`alembic upgrade` в проде. Теперь `legal_constants.py` берёт
  значения из `legal_generated.py`, обычного питоновского файла рядом с
  остальным кодом бэкенда — он едет в образ вместе с ним без исключений в
  Dockerfile и без монтирования тома.

## Как заполнить operator.json после регистрации юрлица

1. Откройте `legal/operator.json`.
2. Замените все значения вида `{{ИНН}}`, `{{ОПЕРАТОР_ПОЛНОЕ}}` и т.п. на реальные
   реквизиты (ИНН, ОГРН, юридический/почтовый адрес, банковские реквизиты, ФИО
   руководителя, домен, почты, тарифы, дату публикации в каждой записи
   `documents[].effective_date`).
3. Проверьте блок `processing` — он должен отражать фактический состав данных,
   сверенный по `backend/app/models/`. Меняйте его при изменении моделей.
4. Установите `"filled": true`.
5. Пересоберите: `python legal/build.py`.

Пока `operator.json` не заполнен, сборка всё равно проходит: в текстах и в
`documents.generated.ts` видны плейсхолдеры `{{...}}` — это ожидаемое поведение,
а не ошибка. После заполнения они исчезают одновременно везде, где
используются, потому что подставляются из одного источника.

## Как пересобрать

```bash
python legal/build.py
```

Требуется `python-docx` (уже входит в `backend/requirements.txt`; для
изолированного окружения — `pip install python-docx`). Внешних markdown-парсеров
не требуется — минимальный парсер markdown встроен в `render_md.py`, этого
достаточно для того подмножества разметки (заголовки `##`/`###`, абзацы, списки,
`**bold**`, `> цитаты`), которое используется в текстах.

Результат:
- `frontend/src/legal/documents.generated.ts` — документы с `kind: "public"` И
  `published` не `false` (поле необязательное, по умолчанию `true`; документ с
  `published: false` на сайт не попадает, но его slug нельзя перечислить в
  `REGISTRATION_CONSENT_SLUGS` в `build.py` — сборка упадёт `BuildError`);
- `backend/app/services/legal_generated.py` — сроки 152-ФЗ и перечень документов
  согласия для регистрации, нужные бэкенду;
- `legal/out/<slug>.docx` — все документы, публичные и внутренние, включая
  неопубликованные (внутренние — с шапкой организации и местом для
  номера/даты/подписи).

Оба выхода строятся из одного дерева markdown-узлов (AST), чтобы структура
документа не могла разойтись между HTML-версией на сайте и .docx-версией для
печати (ПРАВИЛО №6 — один источник истины, два отрисовщика).

## Что генерируется и не правится руками

- `frontend/src/legal/documents.generated.ts` — целиком, включая шапку-комментарий.
  Правки внутри исчезнут при следующей сборке. Меняйте `sources/public/*.md`
  или `operator.json`, затем пересобирайте.
- `backend/app/services/legal_generated.py` — целиком, включая шапку-комментарий.
  Меняйте `operator.json` (блок `deadlines_working_days`) или
  `REGISTRATION_CONSENT_SLUGS` в `legal/build.py`, затем пересобирайте. Файл
  коммитится в репозиторий (не в `.gitignore`) — от него зависит старт
  бэкенда.
- `legal/out/*.docx` — не хранятся в git (`.gitignore`: `legal/out/`), собираются
  локально или в CI по требованию.

## `--check` — для CI и pre-commit

```bash
python legal/build.py --check
```

Собирает всё во временную папку и сравнивает побайтово с тем, что уже лежит в
репозитории (`documents.generated.ts`, `legal_generated.py` и `legal/out/*.docx`,
если они закоммичены или существуют локально). Ничего не перезаписывает. Код
возврата:

- `0` — репозиторий соответствует текущим исходникам;
- `1` — есть расхождение (кто-то поправил `.generated.ts` руками, забыл
  пересобрать после правки markdown, или сборка вообще не детерминирована) —
  печатает список конкретных отличий в stderr.

Удобно повесить на pre-commit хук или шаг CI перед сборкой фронтенда, чтобы
никто не закоммитил рассинхронизированный `documents.generated.ts`.

## Идемпотентность

Повторный запуск без изменения исходников даёт байт-идентичные файлы (сверено
по sha256 при разработке сборщика). Единственная типовая ловушка для .docx —
python-docx кладёт в каждую запись внутреннего ZIP текущее время сборки;
`render_docx.save_docx_deterministic()` перепаковывает архив с фиксированной
датой у каждой записи, поэтому время запуска не влияет на результат.
