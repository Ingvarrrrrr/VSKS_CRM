# Phase 13 — Заявки v3: канбан авторасспределения

## Goal
Превратить `WishesView` в рабочую заявку с авторасспределением позиций по будущим закупкам: пользователь создаёт заявку с произвольным набором товаров, система раскидывает их по колонкам-закупкам (одна колонка = один `product.category`), пользователь корректирует распределение drag-and-drop-ом, ответственный одобряет «всё-или-ничего» → автосоздание N закупок в статусе `wishes`.

## Scope
- **IN:** Канбан внутри заявки (колонки по категориям), DnD позиций между колонками в рамках одной заявки, одобрение all-or-nothing, автосоздание N закупок, `product.category` = required, кнопка выгрузки служебной записки в WishesView, унификация `item-shape="wish"` → `"purchase"` в редакторе позиций.
- **OUT:** Модуль «Склады» (выдача со склада как альтернатива закупке) — отдельная следующая фаза. Частичное одобрение. Drag между разными заявками. Новые статусы закупки (используется существующий `wishes`).

## Fixed decisions (из сессии 2026-04-20)

| # | Пункт | Решение |
|---|---|---|
| D-01 | Канбан внутри заявки | Колонки = будущие закупки, заголовок колонки = `product.category` |
| D-02 | Товары без категории | Колонка «Не определено» (всегда первая) |
| D-03 | Category required | В `AdvancedProductSelector` при создании товара `category` становится обязательным. Миграция: `NOT NULL` со стратегией backfill (дефолт «Прочее» для существующих) |
| D-04 | DnD scope | Только между столбцами **внутри одной заявки**. Нельзя перетащить в уже существующую закупку |
| D-05 | Одобрение | **Всё или ничего**. После одобрения заявка read-only |
| D-06 | Результат одобрения | N закупок в `status='wishes'` (статус уже существует в воркфлоу, новой миграции не нужно) |
| D-07 | Служебная записка | Кнопка выгрузки в WishesView на уровне заявки. Один `doc_type = service_note`. Перенести UI-логику `openDocPicker('service_note')` из CreateOrderView |
| D-08 | Унификация редактора позиций | `PurchaseItemsEditor` уже поддерживает `item-shape` prop. Раскрыть shape `"wish"` → `"purchase"` — полный набор колонок (страна, фото, описание, НМЦК) как в CreateOrderView |

## Open questions for planner
1. **Как группируются позиции в колонки при первом открытии?** — Ответ: автоматически по `product.category`. Если у позиции нет `product_id` (сырой текст) — в «Не определено».
2. **Сохраняется ли распределение между сессиями?** — Да. Нужна колонка `wish_items.target_column_key` (либо `category_override`) или отдельная таблица `wish_distributions`. Планировщик выбирает.
3. **Что с NMCK суммой при DnD?** — Пересчитывается в шапке колонки. Сумма по заявке = сумма по колонкам. Бюджетный чек делается в момент одобрения (сразу для всех N закупок).
4. **Undo при одобрении?** — Нет. Одобрение — терминальное событие. Откат только через удаление закупок + `wish.status='draft'`.
5. **Служебная записка — от какого purchase_id генерировать?** — До одобрения заявки purchase_id нет. Вариант A: новый эндпоинт `GET /api/wishes/{id}/documents/service_note` который формирует служебку из WishItem напрямую (не через purchase шаблон). Вариант B: пересобрать шаблон чтоб он принимал либо purchase либо wish. Планировщик решает (A предпочтительнее — не размывает контракт documents.py).

## Success criteria
1. При открытии заявки в WishesView видно канбан с N+1 колонками (категории + «Не определено»), каждая карточка = позиция заявки с фото/названием/qty/price
2. Drag карточки между колонками обновляет target (опт-PATCH), visual reorder мгновенный
3. Кнопка «Одобрить» создаёт N закупок за один transaction, каждую — с items соответствующей колонки, status=wishes; заявка → `status='approved'`, read-only
4. `category` в форме создания товара в `AdvancedProductSelector` — обязательное поле с валидацией
5. Кнопка «Скачать служебную записку» в WishesView открывает диалог выбора инициатора и генерит docx
6. Unit & E2E: создание заявки → распределение → DnD → одобрение → верификация N закупок в БД
