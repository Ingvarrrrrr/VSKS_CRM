# edge-nginx — разрез инфраструктуры сервера от автодеплоя VSKS

## Зачем

До этого разреза (2026-09-05) один и тот же контейнер nginx держал 80/443
**для всех проектов на сервере** (GALA/VSKS, uniform, trading, sunduk, sizo,
nemakh, n8n, adminer, halliem) — и его конфиг (`nginx/nginx.conf`) лежал
**в git-репозитории VSKS**, откуда его пересобирал/перезагружал автодеплой
VSKS. Ошибка в PR VSKS теоретически могла положить 80/443 для всех сразу,
не только для VSKS — это и произошло 2026-09-04 (10 минут простоя, см.
комментарии в `docker-compose.yml`).

Теперь:

- **edge** (этот каталог) — отдельный compose-проект, устанавливается на
  сервере в `/opt/edge-nginx/` (**вне** git-дерева VSKS, `/opt/vsks-crm`).
  Держит 0.0.0.0:80/443, TLS для всех доменов. Автодеплой VSKS
  (`autodeploy.sh`, `git checkout -f` + `git clean -fd` в `/opt/vsks-crm`)
  физически не может задеть `/opt/edge-nginx/` — разные каталоги.
- **nginx GALA** (`../../nginx/nginx.conf` в этом репозитории) — слушает
  ТОЛЬКО `127.0.0.1:8079`, plain HTTP, отвечает только за
  `gaaala.duckdns.org`. Автодеплой VSKS продолжает пересоздавать/
  перезагружать его как раньше — теперь это уже не риск для соседей.

## Файлы

| Файл | Роль |
|---|---|
| `nginx.conf` | Живой конфиг edge — источник истины для ВСЕХ доменов сервера, кроме внутренней части GALA |
| `docker-compose.yml` | Compose-проект `edge` (контейнер `edge-nginx`, порты 80/443, сеть `vsks-crm_default` как external) |
| `install.sh` | Переключение/обновление на сервере (`switch`, по умолчанию) и откат (`rollback`) |
| `README.md` | Этот файл |

## ⚠️ ПРАВИЛО: этот каталог — единственный источник правил для соседей

Если нужно поменять маршрутизацию НЕ-GALA проекта (новый порт uniform,
новый поддомен и т.п.) — правь **`deploy/edge/nginx.conf` здесь, в git**,
коммить, пушь, затем `sudo bash deploy/edge/install.sh` на сервере. Никогда
не правь `/opt/edge-nginx/nginx.conf` на сервере напрямую без коммита —
следующий `install.sh` (или чей-то ещё) перезапишет ручную правку исходным
файлом из git, и она тихо потеряется.

Обратное тоже верно: в `nginx/nginx.conf` VSKS (git-дерево `/opt/vsks-crm`)
блоков других проектов больше нет и заводить их там не нужно — дубля
конфигурации не возникает (правило №6 CLAUDE.md — один источник истины).

## Установка / переключение

Полный процесс — на сервере, владельцем (Claude Code на прод не ходит):

```bash
# 1. Убедиться, что vsks-deploy.service остановлен ДО push, чтобы автодеплой
#    не откликнулся на push раньше времени (см. install.sh, шапка файла —
#    почему это критично для этого конкретного переключения).
sudo systemctl stop vsks-deploy.service

# 2. Запушить и подтянуть новые файлы в /opt/vsks-crm (git pull, НЕ через
#    вебхук — он остановлен).
cd /opt/vsks-crm && git pull origin claude

# 3. Прогнать install.sh.
sudo bash deploy/edge/install.sh
```

`install.sh` (без аргументов, он же `switch`):

1. Останавливает `vsks-deploy.service` (повторно, для верности).
2. Сохраняет доразрезные `nginx/nginx.conf` и `docker-compose.yml`
   (из git-коммита `PRE_SPLIT_REF`, по умолчанию `HEAD~1`) в
   `/opt/edge-nginx/.rollback/` — материал для `rollback` (см. ниже).
   Делает это **один раз**: повторный запуск `install.sh` не перезатирает
   уже сохранённый снимок.
3. Синхронизирует `deploy/edge/{nginx.conf,docker-compose.yml,README.md}`
   → `/opt/edge-nginx/`.
4. Готовит `/opt/edge-nginx/secrets/adminer.htpasswd` — переносит значение
   `ADMINER_HTPASSWD` из `/opt/vsks-crm/.env` (тот же пароль, что уже был;
   пусто → заведомо неподходящий хеш, adminer честно отдаёт 401, как и
   раньше). Проверяет/создаёт placeholder-сертификат, если реального ещё
   нет (первый запуск на чистом стенде).
5. **Репетиция на запасных портах 8080/8443** — поднимает временный
   `edge-nginx-staging` контейнер с ТЕМИ ЖЕ файлами, что поедут в бой,
   проверяет `nginx -t`, затем curl'ит КАЖДЫЙ домен из единого списка
   `DOMAIN_CHECKS` (в install.sh) — единственная точка истины для
   проверок и на репетиции, и после боевого переключения. **Любое
   расхождение проваливает скрипт до того, как тронуты боевые 80/443.**
6. Боевое переключение:
   - `docker compose up -d --force-recreate --no-deps nginx` в
     `/opt/vsks-crm` — пересоздаёт GALA-nginx на новом конфиге/порту
     (`127.0.0.1:8079`), это освобождает 80/443;
   - **сразу же** `docker compose up -d` в `/opt/edge-nginx` — поднимает
     edge на 80/443. Реальное окно недоступности — время между этими
     двумя командами (пересоздание контейнера nginx:alpine без
     бэкенда/миграций внутри — секунды, не десятки секунд); соседи
     (uniform/trading/sunduk/sizo/nemakh/n8n/adminer/halliem) недоступны
     ровно это же окно, не дольше.
   - проверяет все домены снова, теперь на боевых 443/80.
7. Запускает `vsks-deploy.service` обратно.

Повторный запуск `install.sh` (например после правки `deploy/edge/nginx.conf`)
безопасен: шаги 1-5 отрабатывают так же (в т.ч. репетиция на запасных
портах), шаг 6a для GALA становится избыточным (GALA и так уже на 8079,
`--no-deps nginx` его просто перечитает не мешая соседям), 6b обновляет
`edge-nginx` (`docker compose up -d` пересоздаст его, если изменился
`nginx.conf`/образ — короткая, некритичная для GALA пауза на самих
соседних доменах, аналогичная любому обычному redeploy edge).

## Откат

```bash
sudo bash deploy/edge/install.sh rollback
```

Делает:

1. Останавливает `vsks-deploy.service`.
2. Останавливает/удаляет `edge-nginx` (и staging-контейнер, если завис).
3. Восстанавливает **на диске** `/opt/vsks-crm/nginx/nginx.conf` и
   `/opt/vsks-crm/docker-compose.yml` из сохранённого на шаге 2 `switch`
   снимка (доразрезная версия).
4. Пересоздаёт GALA-nginx на 80/443 со старым конфигом.
5. Проверяет домены.
6. **Намеренно оставляет `vsks-deploy.service` остановленным** и печатает
   предупреждение: пока он остановлен — репозиторий безопасно "грязный"
   (`git diff` покажет расхождение с HEAD); как только вебхук снова
   запустят, следующий push/pull (`git checkout -f`) вернёт файлы к HEAD —
   то есть **обратно к split-схеме**, откат слетит. Это ожидаемо: rollback
   — временная мера на время расследования, а не постоянное состояние.
   Если откат нужен насовсем — `git revert` коммита разреза, а не ручная
   правка файлов на сервере.

## Известные риски / что НЕ решено этой задачей

- **certbot остаётся в compose VSKS** (`/opt/vsks-crm`, сервис `certbot`),
  а не переехал на edge. Это осознанный выбор — минимизация диффа: edge
  просто читает `/etc/letsencrypt` (read-only), а обновляет его по-прежнему
  VSKS-контейнер. Риск: если compose VSKS когда-нибудь полностью
  остановят (например при миграции самого VSKS на другой сервер), продление
  сертификата остановится вместе с ним, а edge — и все чужие домены —
  зависят от этого сертификата. Кандидат на отдельную задачу: вынести
  certbot в `/opt/edge-nginx/` тоже.
- **Вебхуки деплоя** (`/deploy/vsks-crm`, `/deploy/trading-bot`,
  `/deploy/fruits`) остаются нацелены на `172.17.0.1:900x` — тот же адрес,
  что использовал единый nginx раньше. На Linux (прод) это стандартный
  docker0-gateway, работает одинаково что из старого контейнера, что из
  edge — переезд не меняет их поведение. **Не проверено этой задачей на
  проде** (только структурно, см. README и отчёт — реальный webhook-путь
  проверяется отдельно, вне охвата локальной репетиции: 172.17.0.1
  недостижим из контейнеров на Docker Desktop для Windows/Mac, репетиция
  шла на Linux-совместимом стенде WSL2, но настоящий GitHub webhook не
  дёргался).
- **Сторожа `fruits-guard`/`trading-guard`** (systemd-таймеры на сервере,
  вне git — `/opt/fruits-guard/check-vsks-config.sh`,
  `/opt/trading-guard/check-nginx.sh`) сейчас проверяют
  `/opt/vsks-crm/nginx/nginx.conf` на наличие блоков halliem/trading и
  самовосстанавливают их туда, если пропадут. После разреза эти блоки
  живут в `/opt/edge-nginx/nginx.conf`, а не в VSKS — **сторожей нужно
  вручную перенаправить** на новый путь (или выключить и явно предупредить
  владельца, что эти блоки теперь некому восстанавливать). `install.sh` их
  не трогает — это ручной шаг на сервере, вне охвата этой задачи (сторожа
  не в git).
- **`scripts/setup-ssl.sh`** после первого выпуска сертификата делает
  `docker compose exec nginx nginx -s reload` в проекте VSKS — раньше это
  был единственный контейнер с TLS, теперь TLS у edge. Скрипт не обновлён
  в рамках этой задачи (выпуск нового сертификата с нуля — сценарий,
  который на проде уже пройден, GALA сертификат уже существует) —
  когда возникнет реальная необходимость перевыпуска, `docker exec
  edge-nginx nginx -s reload` (или просто подождать штатный 6-часовой
  цикл reload у edge) нужно добавить туда явно.
- **PRE_SPLIT_REF по умолчанию `HEAD~1`** — работает, только если
  `install.sh switch` запускают сразу после того коммита, что ввёл разрез
  (ожидаемый по постановке задачи сценарий: push прямо перед запуском).
  Если между разрезом и запуском `install.sh` было ещё несколько
  коммитов — передать `PRE_SPLIT_REF=<sha до разреза>` явно.
