# {{doc.title}}

Настоящая Модель угроз определяет источники угроз безопасности
персональных данных, актуальные угрозы и меры по их нейтрализации
применительно к ИСПДн «{{site.product_name}}» — веб-приложению
на базе FastAPI (серверная часть) и Vue (клиентская часть),
использующему в качестве хранилища базу данных PostgreSQL,
размещённому на сервере {{hosting.provider}} за обратным прокси-
сервером nginx, с автоматическим развёртыванием обновлений
через webhook при внесении изменений в исходный код.

## 1. Источники угроз

1.1. Внешний нарушитель — лицо, не имеющее легитимного доступа
к ИСПДн, действующее из сети Интернет: попытки эксплуатации уязвимостей
веб-приложения, перебор учётных данных, сканирование открытых портов.

1.2. Внутренний нарушитель с ограниченными правами — авторизованный
пользователь системы {{site.product_name}} (работник организации-
Пользователя), пытающийся получить доступ к данным за пределами
предоставленных ему прав.

1.3. Внутренний нарушитель с полными правами — лицо, обладающее
административным доступом к серверу, базе данных или процессу
развёртывания (на дату утверждения — исключительно
{{responsible.fio}}); риски, связанные с ошибкой или злоупотреблением
таким доступом.

1.4. Технические угрозы, не связанные с действиями нарушителя: сбой
оборудования, программная ошибка, приводящая к утечке или потере
данных.

Оператор не рассматривает в качестве актуальных угрозы, связанные
с наличием недекларированных возможностей в системном и прикладном
программном обеспечении: используется общедоступное типовое
программное обеспечение (PostgreSQL, стандартные библиотеки Python
и JavaScript) без признаков встроенных недекларированных возможностей
и без обработки сведений, составляющих государственную тайну. Отсюда —
вывод Акта определения уровня защищённости об актуальности угроз
3-го типа.

## 2. Актуальные угрозы и меры нейтрализации

### 2.1. Несанкционированный доступ к персональным данным через веб-интерфейс или API системы

Описание: получение доступа к данным, минуя предусмотренную ролевую
модель, — в результате уязвимости в проверке прав (например,
эндпоинт, отвечающий данными без проверки авторизации или без
проверки принадлежности данных организации запрашивающего), подбора
или перехвата учётных данных, использования типовых веб-уязвимостей
(внедрение кода, подделка межсайтовых запросов).

**Разбор произошедшего инцидента.** В одном из смежных проектов
Оператора незащищённый GET-эндпоинт возвращал персональные данные
без проверки авторизации запроса — данные были доступны любому, кто
знал или подобрал адрес запроса, без предъявления токена доступа.
Этот случай учтён как типовой сценарий данной угрозы и включён
в перечень проверок Регламента реагирования на инциденты безопасности
персональных данных.

Меры нейтрализации: обязательная проверка токена доступа
и принадлежности запрашиваемых данных организации пользователя
на каждом эндпоинте, возвращающем персональные данные; передача
данных исключительно по защищённому протоколу (HTTPS); хеширование
паролей необратимым алгоритмом; ограничение времени жизни токена
доступа; включение проверки авторизации и разграничения по организации
в обязательный перечень при code review новых и изменяемых
эндпоинтов, отдающих персональные данные.

### 2.2. Утечка персональных данных через резервные копии

Описание: получение несанкционированного доступа к резервной копии
базы данных, содержащей полный слепок персональных данных, в обход
средств защиты, применяемых к работающей системе.

Меры нейтрализации: хранение резервных копий на той же защищённой
инфраструктуре, на территории Российской Федерации; ограничение
доступа к резервным копиям кругом лиц, указанным в Списке лиц,
допущенных к обработке персональных данных; исключение передачи
резервных копий по незащищённым каналам связи и хранения их вне
контролируемой инфраструктуры.

### 2.3. Компрометация учётных данных пользователя или администратора

Описание: получение чужого пароля или токена доступа в результате
подбора, перехвата, фишинга или использования простого пароля;
получение доступа к административной учётной записи ИСПДн.

Меры нейтрализации: хранение паролей в необратимо хешированном виде;
рекомендации по минимальной сложности пароля; аутентификация
администратора ИСПДн по ключевой паре при удалённом доступе к серверу,
без парольного доступа по SSH; журналирование входов и действий
пользователей; возможность принудительной смены пароля и отзыва
активных сессий при подозрении на компрометацию.

### 2.4. Действия администратора (внутреннего нарушителя с полными правами)

Описание: ошибочное или недобросовестное действие лица
с административным доступом к серверу, базе данных или процессу
автоматического развёртывания — прямое изменение данных в обход
приложения, выгрузка данных сверх необходимого, внесение в код
изменений, ослабляющих проверки доступа.

Меры нейтрализации: минимизация числа лиц с административным
доступом (на дату утверждения — одно лицо, следующее одновременно
из организационной структуры и Списка лиц, допущенных к обработке
персональных данных); использование персональных, а не общих учётных
записей для административных действий; хранение исходного кода
и истории его изменений в системе контроля версий, позволяющей
установить автора и содержание каждого изменения; применение
изменений к работающей системе только через автоматическое
развёртывание из подтверждённой версии кода, а не путём произвольного
редактирования файлов на сервере в обход контроля версий.

### 2.5. Компрометация процесса автоматического развёртывания (webhook)

Описание: получение возможности инициировать развёртывание
произвольного кода на сервере в обход системы контроля версий —
через компрометацию секрета webhook или самого механизма приёма
уведомлений о новых изменениях.

Меры нейтрализации: секрет для приёма уведомлений о развёртывании
хранится вне исходного кода (в переменных окружения сервера, не
в открытом репозитории); эндпоинт приёма уведомлений проверяет
подлинность источника перед запуском развёртывания; межсетевой экран
сервера ограничивает доступ к служебным портам и сервисам, не
предназначенным для внешнего использования (в том числе к прямому
доступу к базе данных, административным панелям вспомогательных
сервисов), оставляя доступными извне только порты, необходимые
для работы веб-приложения по защищённому протоколу и административный
доступ по ключу.

### 2.6. Угроза, связанная со сведениями о местоположении работника

Описание: наиболее чувствительная категория персональных данных
Оператора — координаты местоположения работника — представляет
повышенный риск при утечке (возможность отслеживания перемещений
человека). Актуальны те же угрозы несанкционированного доступа
(2.1) и компрометации учётных данных (2.3), но с повышенной тяжестью
последствий.

Меры нейтрализации: дополнительные к общим мерам, специально
для данной категории — ограничение круга лиц, которым доступны
координаты, ролевой моделью (Правила доступа к персональным данным
в информационной системе, п. 2.3); запрет на включение координат
в файлы журналов работы сервера; автоматическое удаление точек
местоположения по истечении {{processing.geolocation_retention_days}}
дней; отдельное информированное согласие работника (Форма уведомления
и согласия работника на определение местоположения) с правом отказа
и отзыва.

### 2.7. Перехват персональных данных в канале связи

Описание: получение персональных данных при передаче между браузером
пользователя (клиентом мобильного приложения водителя) и сервером
ИСПДн.

Меры нейтрализации: сертифицированные ФСБ России средства
криптографической защиты информации (СКЗИ) не применяются; канал связи
защищён протоколами TLS 1.2/1.3 (HTTPS) штатными средствами веб-сервера
и браузеров; угроз, нейтрализуемых исключительно применением СКЗИ,
не выявлено. Приказ ФСБ России от 10.07.2014 № 378 распространяется
на операторов, применяющих СКЗИ (пункт 2 указанного приказа), и к
Оператору не применяется. Раздел подлежит пересмотру при подключении
ИСПДн к государственным информационным системам, начале обработки
специальных категорий персональных данных или изменении оценки
актуальных угроз.

### 2.8. Паспортные данные и СНИЛС контрагентов — физических лиц по договорам ГПХ

Описание: Оператор обрабатывает паспортные данные (серия, номер, кем
и когда выдан), СНИЛС, дату рождения и адрес регистрации контрагентов —
физических лиц, с которыми заключён договор гражданско-правового
характера (поле `org_type = 'Физ.лицо'`, модель
`backend/app/models/contractor.py`: `passport_series`,
`passport_number`, `passport_issuer`, `passport_issued_date`, `snils`,
`registration_address`, `birth_date`). Эти данные нужны для подготовки
и исполнения договора ГПХ (реквизиты стороны договора, налоговая
отчётность) и не относятся к специальным категориям (раздел 1 Акта
определения уровня защищённости, п. 3.1 — иные категории персональных
данных). Справочник контрагентов — общий для всех организаций-
Пользователей и всех авторизованных пользователей ИСПДн (намеренное
решение: при создании закупки/договора любой пользователь должен
видеть любого контрагента в автоподборе), в том числе контрагентов,
созданных другой организацией-Пользователем. Актуальная угроза —
просмотр паспортных данных и СНИЛС физического лица пользователем,
не имеющим отношения к договору с этим контрагентом, то есть избыточный
по сравнению с целью обработки доступ.

**Запланированные меры** (на дату утверждения не реализованы):
ограничение выдачи полей `passport_series`, `passport_number`,
`passport_issuer`, `snils`, `registration_address`, `birth_date`
в ответе API только пользователям, имеющим отношение к договору
с данным контрагентом (автор, участник организации, стороной которой
является договор, либо роль с административным доступом), — остальным
пользователям эти поля не передаются, а не только скрываются в
интерфейсе; до реализации действуют общие меры — обязательная
аутентификация для доступа к справочнику контрагентов (2.1) и
минимизация состава полей, запрашиваемых в типовых формах создания
контрагента, до фактически необходимых для текущей операции.

## 3. Вывод

Совокупность организационных и технических мер, перечисленных
в разделе 2, признаётся достаточной для нейтрализации актуальных
угроз безопасности персональных данных при установленном 4 уровне
защищённости (Акт определения уровня защищённости персональных
данных). Настоящая Модель угроз пересматривается при изменении
архитектуры ИСПДн, состава обрабатываемых персональных данных
или выявлении новых угроз, в том числе по результатам расследования
инцидентов (Регламент реагирования на инциденты безопасности
персональных данных).
